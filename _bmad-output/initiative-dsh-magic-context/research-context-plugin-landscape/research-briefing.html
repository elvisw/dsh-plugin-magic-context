上下文插件竞品与开发价值评估

决策：是否继续独立开发 dsh-magic-context。 访问日：2026-11-09。

证据分级：源码支持表示本次读取了实现；作者自述表示来自维护者文档；发行证据表示注册表/CI记录存在。均不等于本机运行验证。没有独立的不同数据源确认时，承重声明仍记为 medium / unverified，不是断言虚假。

决策摘要

medium / unverified · 非运行验收

不建议按当前“大而全的DSH版Magic Context”方向从零重做。建议先采用并验证wk544863858/dsh-plugin-magic-context，把本项目暂时定位为差距验证与可贡献扩展。 源码与作者文档显示，其范围包含可逆工具回收、Historian、持久记忆与基础UI。本项目尚未证明存在这样的关键场景：现成方案无法满足，且用户确实需要。[2][3][8]

这不是建议删除项目或立即安装依赖。现有需求与研究仍可作为验收清单；只有出现可复现的关键缺口，再比较上游贡献、受限fork和独立实现的成本。以下是产品建议，不是已批准的PRD变更。

跨宿主替代与参考

medium / unverified · 非运行验收
项目 类别与本次证据 对本项目的意义
Magic Context / CortexKit OpenCode、Pi、OMP上的完整上下文管理与记忆体系：缓存感知回收、Historian、Dreamer、跨会话搜索和原文展开；官方README称Pi与OpenCode共享数据库。[16] 完整能力的上游参考，不是可直接装进DSH的插件；“跨宿主记忆”本身也已有方案，DSH接入价值需单独证明
Dynamic Context Pruning / DCP OpenCode请求侧压缩，当前单compress工具，range及message（实验性）两模式；不修改宿主历史。已读decompress源码显示压缩块可置为inactive；底层消息恢复的完整路径未逐行复核或运行验收。[17][18] 不能误称纯永久删除。但块级解压不等于本项目所有稳定引用、跨会话检索和记忆需求；作者明确新工作优先转往Sleev。[17]
claude-mem 工具活动→observations→跨会话检索与注入；调研摘要核到2026-11-09仍有release。[19] 是跨会话观察式记忆的替代层，不等于卸载工具输出后逐项恢复原文；不要因有记忆功能就视为完整替代
Sleev 本地代理层上下文优化；厂商宣称支持多种coding harness。DCP维护者明确迁移开发重心，技术主张未独立验证。[17][20] 对“再做一个通用压缩器”构成路线竞争；DSH接入、精确恢复、隐私与回退细节均未确认，不推荐直接替代安装
opencode-recall 早期工具I/O落盘方案，保留blob指针并用rcl_restore读回快照；已读源码默认超8KB拒绝，force可覆盖。[21] 说明“落盘＋指针＋按需读取”也已有实现；0.1.0及较早的更新记录不足以支持将其直接当作成熟替代；8KB是拒绝阈值而非静默截断

反向证据： 竞争确实存在，但这些方案并非全部等价，也没有本次实测能证明任一方案完整满足本项目八组需求。DSH的跨会话原文搜索、Smart notes及与上游数据互通仍是待核实缺口；上游MC已有对应能力，不代表其DSH适配已完成。[16] 不能据此直接判定项目“毫无价值”。同会话跨窗口的历史原文读取已有方案，不能再把它单独当作空白市场；观察记忆的recall则仅限按已知记忆ID查证，不是任意历史读取。[10][11][12]

指定项目：核心范围已有实现与文档证据

medium / unverified · 非运行验收

wk544863858/dsh-plugin-magic-context 是本项目最直接的替代，而不是名字相近的普通记忆插件。

  • 已经发布，而不是只有规划：npm latest=0.11.1，gitHead=93ef5fe4a06a2c05f53e6a6225346919e860d74e；changelog记载2026-11-07更新，当日对应CI成功。[1][7][9]
  • 核心闭环有源码及测试代码，未在本次执行：ctx_reduce只入队；ctx_expand(tags)寻找当前surface上的占位符，沿sourceEventSeqs读取原始工具结果content，再替换回surface。已读恢复路径不重新执行原工具，也不生成替代摘要。集成测试代码使用真实DSH agent loop和MockAdapter，编写了原正文→占位符→原正文的断言，不代表本次已跑通。[3][4][5]
  • 作者文档描述的范围广于我们尚未实施的阶段0：列出四层Historian、项目SQLite记忆、FTS＋本地向量、共享域、维护tick、GUI设置及遥测。按README，默认不接管宿主compaction-basic；若启用接管，要处理互斥配置。[2]
  • 仍不是完整Magic Context移植：独立ctx_search、ctx_note未见于已读工具接口；记忆检索用ctx_memory(action=search)，不等于跨会话的原始历史全文检索。[2][3] 作者明确独立维护自有corpus，不承担上游数据库互读义务；完整Dreamer、watermark age reclaim、精确tokenizer及图像计量未移植，并非完全没有计量（仍有chars/4估算）。[8]
  • 兼容性有待测，而不是已证明不可用：已读ci.yml配置为ubuntu-latest＋Node22/24，未穷尽其他工作流；本次没有Windows安装、DSH0.2.2-rc.1运行或重启测试。README的0.2.1-rc.1源码基线与新changelog提到的0.2.2-rc.1应区分，不能拿旧锚点直接宣布不兼容。[2][6][9]

真正可能形成差异的方向

medium / unverified · 非运行验收
  • 可审计的长程恢复契约：同会话跨窗口读取原文已有其他DSH插件；更值得验证的是重启、再次压缩、Historian遮蔽及跨会话后，稳定引用和完整性保证是否一致。如现有方案已满足，就不另做。[3][4][5][10][11]
  • 跨宿主迁移或互通：指定竞品明确不承担MC存储互读义务，因此这里有边界差异；但本项目OQ-2尚未确认它是否首版必需，不能先造需求。[8]
  • Windows/DSH兼容验收与回归套件：提供能运行、能复查的证据；公共Ubuntu CI未覆盖的部分是验证机会，不是现有产品缺陷的证明。[6]

这些方向首先是贡献或验证机会。只有在用户确需、现有插件有可复现缺口且维护者不接受兼容扩展时，才足以支持受限fork或独立实现。使用较新上游基线、换存储目录或再写一层adapter，本身都不是用户收益。
